## Architecture choices and why

1. **Two apps, not one Next.js app.** The cost is two deploys. The gain is that business rules can't leak into UI code, and you get a real backend to show. It's worth it because the backend is where you want to stand out, and the cost is paid once in the skeleton step.

2. **A modular monolith with three modules.** Catalog, cart and orders are the nouns of the buying path. Payments live inside orders, because a payment only exists to settle an order; a separate payments module would just pass data back and forth.

3. **Each module is split into routes, service and repo:**
   * **Routes** handle HTTP only. They check the input with Zod and call the service.
   * **Service** holds the rules, such as "price comes from the database" or "a payment is never counted twice". It never sees `req` or `res`.
   * **Repo** is the only code that writes SQL, through Drizzle.

   This gives each file one job, and the most important rules can be tested without HTTP. It's the one layer of structure I'd add. No dependency injection container, no interfaces for single implementations, no event bus.

4. **The browser talks to one domain.** Next.js forwards `/api/*` to Railway, so the cart cookie belongs to our own site and needs no CORS setup. Server components call the API directly for speed.

5. **No accounts.** The cart is identified by a cookie. An order is found by its unguessable UUID, which works like a private link. This is a product choice as much as a shortcut: Amazon forces you to sign in before checkout, and we don't.

6. **`web/` has no business logic.** It never computes a total or checks stock. It displays what the API says, so there is one source of truth.
